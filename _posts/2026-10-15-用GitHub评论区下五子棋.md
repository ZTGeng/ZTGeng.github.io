给网站加了评论功能之后，我突然觉得，评论区这个东西，好像还可以拿来下棋。
<!--more-->

我的网站托管在 GitHub Pages 上，只有静态页面。最近加了 giscus，它会把网页上的评论存在 GitHub Discussions 里，用户用 GitHub 账号登录，就可以发表评论。

既然能发表评论，也能读取评论，那把评论内容换成棋盘数据，不就可以做一个在线五子棋了吗？

甲下一手，更新评论。乙读取评论，看见甲下在哪里，再下一手。围观群众也读取同一份评论。

我不需要服务器就可以运行一个多人在线游戏！

GitHub 莫名其妙多了一份工作。

## 1. 先解决登录

这次想做的事情很明确：不搭自己的服务器，只用静态网页和现成的服务，把多人对局跑通。

本来想直接借用 giscus 的登录。用户已经在评论框里登录了 GitHub，我顺便用一下这个身份，应该很合理吧。

结果不行。giscus 的评论框在一个独立的 iframe 里面，不会把用户的 token 交给我的网页，也没有提供一个接口，让我随便读取里面的评论数据。

能看见评论框，不等于我的 JavaScript 能拿到评论。

那就自己登录。GitHub 提供 GraphQL API，可以查询 Discussion，也可以创建、编辑、删除评论。问题变成了：怎么让一个静态网页拿到用户授权的 token？

常规的 OAuth 登录流程有一步需要用 Client secret 换取 token。secret 显然不能直接写进公开的网页源码里。为了登录再搭一个后端，又绕回去了。

最后用了 Firebase Authentication。

在 GitHub 注册一个 OAuth App，把 Firebase 提供的回调地址填进去，再把 Client ID 和 Client secret 填到 Firebase 控制台。网页用 Firebase SDK 弹出 GitHub 授权窗口，登录成功后，从结果里取出 GitHub access token。

整个过程可以写成：

```
静态网页 → Firebase → GitHub 授权
静态网页 ← GitHub access token

静态网页 → GitHub GraphQL → Discussion
```

Firebase 只管登录。棋盘没有存在 Firebase，也没有通过 Firebase 转发游戏请求。拿到 token 之后，浏览器自己去找 GitHub。

所以“不用服务器”是说不用我自己部署和维护一个游戏服务器。GitHub 和 Firebase 的服务器还是要上班的，它们只负责用户登录而已。

## 2. 一局棋，两条评论

最初的想法是一局棋对应一条评论，双方轮流编辑。评论内容就是当前棋局的状态。

但是这个评论用谁的帐号来发？想了想应该让用户自己发。我总不能在网页里放一个站长 token 给所有人共用。

但是用用户的账户来发，对手就不能编辑。自己发的评论只有自己（和站长）可以编辑。

所以改成一局棋对应两条评论，每人只编辑自己的那条。评论里用 JSON 保存对局 ID、玩家身份、对手评论 ID，以及落子记录。

棋盘状态保存的是一串坐标：

```
黑方记录：第1手，第2手，第3手
白方记录：第1手，第2手
```

白方读到黑方的新记录之后，接着下第4手，再把自己的评论更新成前4手。黑方下一次读取时就能看到。

两份记录有点重复，但有一个好处：正常情况下，短的应该是长的的前缀，两边最多差一手。可以据此检查数据有没有分叉，不能单纯看哪条评论更新时间晚，就把它当成最新棋盘。毕竟认负、确认结果也会更新评论，但不一定增加棋子。

另外还考虑过每局单独开一个 Discussion，再用一个主 Discussion 维护大厅列表。

这样每局的数据倒是分开了，但是谁来维护主列表？普通玩家不能随便编辑我的主帖。如果再通过评论维护列表，又多了一套需要同步的数据。一局棋创建成功了，列表更新失败了怎么办？

想了一圈，暂时还是把所有对局都放在同一个 Discussion 下面。大厅加载时把评论读出来，在本地拼成对局列表。进入对局后，已经知道双方评论的 ID，就只读这两条，不用每五秒把整个评论区翻一遍。

规模大了肯定要重新考虑。但现在先让两个人能下完一盘棋。

## 3. 五秒钟看一次，对手下了没有

GitHub 不会往这个静态网页里主动推送落子消息。所以只能轮询。

五子棋倒是很适合低频轮询。下完一手，等几秒钟很正常。如果做成格斗游戏，每五秒问一次对手出了什么招，那就不OK。

但是轮询读取 Discussion 需要调用 GraphQL API。API 也不是无限用的，每个账号有自己的调用额度，每小时5000点。

每次查询花1点。每五秒查一次，一个小时就是720点。再加上加载大厅、落子前检查和写入的点数。所有这些点数都只能让用户自行承担了。我总不能在网页里放一个站长 token 给所有人共用。

这就是为什么所有人都要登录，包括只想旁观的人。每个人用自己的 token 读取数据，消耗自己的额度。

点数消耗尽量压低：

- 轮到对手行动，每五秒看一次动了没有。
- 轮到自己时，停止轮询，等用户输入，真正提交前再读一次最新状态。
- 切到后台时暂停，回到页面再同步。
- 大厅先不自动刷新，要手动点击刷新。

大厅的缩略图只显示前十几局，不代表只需要读取前十几条评论。为了找到我自己的对局、把双方记录配起来，并按最近活动排序，当前实现还是要分页扫描整个 Discussion。

将来用户多起来（想peach），对局多了，评论就会变多，大厅就会慢。

所以开始考虑清理，把结束的对局删除掉，缩短评论长度。

## 4. 下完了，谁来收棋盘

最开始觉得很简单：对局结束，把两条评论删掉就行。

然后发现，如果我赢了，马上把自己的评论数据清掉，对手还没来得及轮询，就不知道我最后一手下在哪里了。

甚至都不知道我下没下，我也可能点了认输。这些都需要在数据清理之前同步给对方。

更麻烦的是，他可能刚好把网页关了。现在谁也不知道他什么时候回来。数据可能永远同步不了了。

于是开始讨论各种情况：一方删了另一方没删，两边状态不一致，正在大厅的人顺便检查一下，有没有必要再加一个删除确认……

越讨论越复杂。五子棋本身的逻辑一遍过，收棋盘反反复复来回改。

最后决定先收紧操作规则：对局开始后就不能返回大厅，除非认负结束掉这局棋。结束的棋局才可以返回大厅。这样就强制用户留在对局页面同步结果。

当然这不能阻止用户关网页，但能少制造一些正常操作下的不同步。

然后给每个人的数据加三个字段：

```
acknowledged：我已经确认对局结束
winner：谁赢了
reason：五连、认负，或者和棋
```

产生结果的一方先写入结果。另一方读到之后，自动把同样的结果写进自己的记录。双方都确认了，之后加载大厅时，就可以清理自己的那条评论。

如果我已经确认结束，对方的评论也已经不在了，说明剩下这条也可以收走。反过来，如果对方还没确认，我就先留着自己的记录，等他回来读取。

如果对局在我关网页的期间结束了，下次我回来打开，会先读到结果，完成确认。

双方确认，下次进大厅就会触发清理。

不要求两个人的页面在同一瞬间变成同一个样子，只要回来之后能把事情办完就行。

## 5. 目前能下了

用另一个 GitHub 账号和主账号完整下了一局，创建、加入、落子、结束都跑通了。

没有做排名、聊天、悔棋，也没有另建一个地方保存历史棋谱。项目目前只有最基本的功能，毕竟只是为了验证这种模式。

游戏在这里：[在线五子棋](/games/online-gomoku/)。需要 GitHub 账号和授权，登录页写了具体说明。当前请求的 `public_repo` 权限范围比“只往我的游戏帖子里下棋”大，不能把它理解成一个仅限这盘棋的授权。

回头看，最初那个“把棋盘存在评论里就可以甩开服务器”的想法，确实是能行的。

只不过下棋之前需要登录；下完棋之后，还得研究怎么删评论。
