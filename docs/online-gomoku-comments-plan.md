# 在线五子棋大厅留言功能方案

状态：首版已实现，待真实账号验收。用户已指定 [Discussion #6](https://github.com/ZTGeng/ZTGeng.github.io/discussions/6) 为留言帖；配置使用 owner/name/number，加载时解析其 node ID。大厅已移除 giscus；其他页面的 giscus 保持原样。

实现：`shared/discussion-comments.js` 为不依赖框架和游戏的状态模块，`games/online-gomoku/messages.js` 为可注入登录身份、API、写调度的双语界面。`github.js` 处理专用分页与定向写入，拒绝向棋谱帖发表留言。界面只在大厅可见，初次读取不阻塞棋局展示，游戏操作开始时取消留言读取；写入借用现有任务和写锁串行化。留言错误局部显示，401 使用统一退出流程。pending 发表按用户及目标帖持久化，普通草稿只留内存。

验证：38 项核心测试及模拟浏览器流程通过，覆盖分页、去重、HTML 作为纯文本显示、权限删除、响应丢失后刷新核对、游戏清理隔离和既有双人游戏流程。真实 #6 发表/删除与跨账号显示待用户验收。

## 目标与范围

在大厅底部提供简单留言区，复用游戏登录取得的 GitHub token。浏览器直接调用 GitHub GraphQL，不增加服务器、云函数、代理、Firebase 数据库或额外授权步骤。所有读取和写入使用当前玩家的额度。

首版支持：查看留言、发表留言、删除自己的留言、管理员删除有实际权限删除的留言、手动刷新和加载更早留言。显示 GitHub 用户名、发表时间及原帖链接。只在大厅显示；留言失败不阻断大厅、配对或恢复对局。

首版不支持：编辑、嵌套回复、点赞、实时聊天、Markdown 预览、附件、搜索、未读提醒和自动归档。需要完整讨论时可通过链接进入 GitHub。

## 数据存储

- 单独使用一个 Discussion 作为大厅留言板，绝不复用存放棋谱的 Discussion #5。
- 站长已创建并指定允许玩家评论的 Discussion #6。配置其 number，读取时取得 node ID，不手工猜测 ID，也不由前端自动创建 Discussion。
- 每条留言就是一条顶层 Discussion comment。正文直接保存用户文本，不套用棋局 JSON 协议。
- 作者、时间、权限以 GitHub API 返回字段为准，不在正文重复保存。
- 棋局扫描、终局清理和管理员棋局清理只针对原来的游戏 Discussion，不涉及留言。留言保留，不按 30 天游戏清理规则自动删除。

## 界面与加载

1. 大厅棋局区域下方显示“留言”标题、输入框、发表按钮、刷新按钮和留言列表。支持现有 SiteUI 中英文切换。
2. 大厅数据完成并确认用户留在大厅后，再独立加载最新 20 条留言，不拖慢棋局展示或自动恢复。进入对局时不新增留言请求；会话结束后丢弃缓存与草稿，旧响应不得更新新会话。
3. 按创建时间倒序显示，最新在上。使用 `comments(last:20)`；加载更早时使用 `last:20, before:startCursor`，读取 `hasPreviousPage`。将返回页反转后按 ID 去重，不扫描全部留言。
4. 本次登录内缓存已加载列表，返回大厅先展示缓存；无后台自动刷新。刷新重新读取最新一页并重置分页，避免把旧页当成完整实时列表。
5. 输入按纯文本显示，保留换行，使用 `textContent`，不直接注入 `bodyHTML`。在 GitHub 原帖中写入的 Markdown 在大厅显示为原始文本。空白内容不可发送，网页暂定限制 1000 字符，输入区显示计数；此为产品限制，不声称是 GitHub 上限。
6. 删除按钮依据 `viewerCanDelete` 显示，含一次确认；管理员也以 GitHub 实际权限为准。删除后更新列表，不额外全量刷新。没有权限的操作由 API 错误反馈。
7. 加载、发送、删除都有局部状态，网络失败保留输入内容；留言错误不覆盖游戏的状态提示。登录失效则使用现有统一退出/重新登录流程。

## 请求与额度

- 复用同一个 `GitHub` 实例的 `request` / `write`、限流退避、额度回调和会话取消机制；不要新建另一个互不知情的请求实例。
- 新增专用分页方法和接受明确 Discussion ID 的留言创建方法。当前 `add(body)` 固定写入游戏 Discussion，不能直接用于留言，避免把留言写进棋谱数据。
- 读取字段复用现有评论字段，含作者 ID 和头像，以及分页信息；返回时一并读取 `rateLimit`。作者为空时显示已删除账号。作者 ID 用于验证未确认留言的归属。
- 大厅留言不轮询。若每次查询 cost 为 1，首次加载增加约 1 点，每次刷新或加载更早再增加约 1 点；实际值以响应为准，写入和查证另计。
- 留言任务在游戏请求空闲时执行，不能与落子争抢写入调度；共用写入间隔和主/次级限流。额度不足显示等待时间，保留草稿。
- 发表期间禁用重复提交。每次提交生成 UUID，在正文末尾附带不可见 HTML 注释 `<!-- gomoku-message:UUID -->`；大厅只剥离末尾符合格式的标记。页面维护本账号未确认发送的信息，与棋局 pending 数据分开。
- 若发表请求超时，不自动重发。按该 Discussion 的最新分页向前查找同作者、同 UUID 的记录，找到即视为成功。查证按需进行，不无限自动扫描；查不到不等于未发送，可继续查找或去 GitHub 核实，用户明确放弃后才允许重新发表。刷新后也应保留当前用户的未确认发送信息。
- 删除超时先按 ID 查证，确认缺失才从列表移除；权限错误不能当成已删除。

## 实施顺序与验证

1. 确定留言 Discussion，添加独立配置；检查帖子与棋谱帖子 ID 不同。
2. 在 `github.js` 添加分页读取和定向创建接口，沿用已有删除能力；补齐专用留言状态和请求调度。
3. 新建 `messages.js` 负责列表、分页、缓存、发送查证及草稿；在 `app.js` 的大厅显示/退出会话时挂接生命周期。HTML/CSS 使用现有布局和双语服务。
4. 使用模拟 API 验证最新页与更早页排序/去重、留言帖子隔离、纯文本展示、超时后查证不重复发送、失效登录响应隔离。浏览器检查大厅/对局切换、移动端和双语。
5. 两个真实账号验收：只登录游戏即可留言；互相能读取，普通用户不能删除他人留言；留言不被棋局清理删除。管理员跨用户删除另按实际权限验证。

API 依据：[GitHub Discussions GraphQL 文档](https://docs.github.com/en/graphql/guides/using-the-graphql-api-for-discussions)，包含评论游标分页与增删接口。本方案采用其已有 API，不需要额外评论框架。
