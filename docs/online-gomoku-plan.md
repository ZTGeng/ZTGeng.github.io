# 在线五子棋实施方案

状态：首版已实现，用户已用两个授权账户完成一局真实对局。Firebase 项目 `ztgeng-online-gomoku`、GitHub OAuth App、授权域名和 Discussion #5 已配置；当前账号的真实登录、身份/额度读取、测试评论创建/编辑/删除，以及创建棋局、刷新恢复、取消棋局均已由用户验证。两个测试账号是否均为非仓库协作者未单独确认；第三人旁观和跨用户管理员清理等验收仍待进行。

## 1. 目标与首版范围

- GitHub Pages 托管全部游戏代码；不部署自有服务器、云函数或 API 代理。
- Firebase Authentication 只负责 GitHub OAuth；浏览器取得玩家自己的 GitHub access token 后，直接调用 GitHub GraphQL。
- 对局记录全部保存在 `ZTGeng/ZTGeng.github.io` 的一个专用 Discussion；每位参与者维护自己的顶层评论。
- 必须登录才能加载大厅、对局和旁观数据；不使用站长 token 或 installation token 兜底。
- 15×15 棋盘，房主黑先，房主在创建时选择是否有禁手，按照正常五子棋规则判断胜负，满盘无胜者和棋。
- 包含登录、恢复对局、大厅缩略图、创建、加入、旁观、落子、认负退出、结果和管理员清理。
- 大厅默认手动刷新，初始显示最新 12 局，提供加载更多；对局等待与旁观默认 5 秒刷新。
- 首版不实现悔棋、计时、排名、聊天、独立历史归档或后台定时清理。等待房间可由房主取消。
- 终局确认/清理已按后续确认的简化规则实现：进行中的玩家不可返回大厅，认负后留在棋盘；只有结果接收方弹出非阻塞终局提示。新增规则通过本地和模拟浏览器验证，用户随后确认已验证。

## 2. 仓库接入

新建 `/games/online-gomoku/`，使用原生 JavaScript ES modules、Bootstrap 和现有 `SiteUI`，不引入统一构建流程。Firebase 浏览器 SDK 固定版本引入。

建议文件：

| 文件 | 职责 |
| --- | --- |
| `index.html` | Jekyll 页面入口、导航、登录/大厅/对局/清理界面 |
| `styles.css` | 响应式棋盘、缩略图、状态样式 |
| `config.js` | Firebase 公开配置、仓库与 Discussion 标识、管理员 GitHub ID、轮询参数 |
| `auth.js` | 授权、GitHub token 保存、身份校验与退出 |
| `github.js` | GraphQL 请求、分页、按 ID 读取、评论增改删、额度和错误解析 |
| `protocol.js` | 评论解析、作者校验、房间配对、棋谱合并与状态推导 |
| `rules.js` | 纯函数：落子、轮次、五连、禁手、满盘判断 |
| `sync.js` | 轮询、退避、取消过期请求、等待申请增量发现 |
| `app.js` | 页面状态、按钮操作、棋盘和大厅渲染 |
| `tests/` | 核心规则、协议和同步异常测试，不依赖真实凭据 |
| `README.md` | 外部配置、运行、联调、限制与清理步骤 |

保留现有 `/games/gomoku.html` 的本地双人玩法。在 `games/index.md` 增加独立在线游戏入口；沿用站点导航、页脚和 `SiteUI.onLanguageChange`，切换语言不重置对局。

此页面不添加普通 giscus 评论组件。

## 3. 外部配置与第一阶段验证

需要在平台控制台完成：

1. 创建 Firebase 项目和 Web App，仅启用 Authentication 的 GitHub provider。
2. 注册 GitHub OAuth App，将 Firebase 提供的回调 URL 填入 GitHub。
3. 将 GitHub Client ID / Client Secret 填入 Firebase 控制台，secret 不进入仓库。
4. Firebase 授权域名加入 `ztgeng.com`、需要使用的 GitHub Pages 域名和本地联调域名。
5. 使用允许普通用户评论的 Discussion 分类，创建专用游戏数据 Discussion；不复用文章评论线程。
6. 填入 Firebase 公开配置、Discussion number/node ID、仓库标识与管理员 GitHub node ID。

先做真实浏览器的最小验证页，再做完整 UI：

- 普通账号通过 Firebase 弹窗授权，取得 GitHub provider token，请求 `public_repo` scope。
- 查询 `viewer { id login }`，确认返回的是当前 GitHub 用户。
- 非仓库协作者能读取游戏 Discussion、创建自己的评论、编辑并删除自己的测试评论。
- 第二个普通账号能读取第一人的记录并创建自己的记录，但不能编辑对方记录。
- 记录查询 `rateLimit.cost/remaining/resetAt`，确认请求使用用户 token。
- 管理员账号验证 `viewerCanDelete`，确认可清理普通用户的测试评论。

以上链路全部通过后，才能确认普通玩家端到端权限；目前当前账号 CRUD 和双账号对局通过，非协作者身份与管理员跨用户权限待单独确认。测试评论明确标记并在联调后清理。

## 4. 登录与会话

- 登录页先解释实验目的、Firebase 认证角色、公共棋局可见性、`public_repo` 的实际授权范围，以及在 GitHub 撤销授权的方法。
- GitHub token 默认保存在 `sessionStorage`；提供可选“记住登录”时改用 `localStorage`。页面配置和日志都不得包含 token。
- 存储访问失败时退回内存会话，并提示关闭页面后需要重新登录。
- Firebase 登录状态不代替 GitHub token。恢复会话后先验证 GitHub 身份，失败则重新授权。
- 首版不实现 provider refresh token 轮换；GitHub token 失效时重新授权。
- 退出清除两类存储中的游戏 token、Firebase 会话和内存数据，停止轮询；其他标签页在恢复焦点或收到退出通知时同步退出。

## 5. 评论协议

所有协议记录均为专用 Discussion 下的顶层评论；不使用嵌套回复。正文使用协议标记和 JSON code block，普通文本或未知协议记录忽略，绝不将评论正文作为可执行 HTML 插入页面。

示例（房主）：

```json
{
  "protocol": "gomoku-v1",
  "gameId": "UUID",
  "userId": "GitHub-user-node-ID",
  "role": "black",
  "forbidden": false,
  "resigned": false,
  "acknowledged": false,
  "winner": null,
  "reason": null,
  "hostCommentId": null,
  "opponentCommentId": "accepted-white-comment-node-ID",
  "status": "playing",
  "moves": [[7, 7], [8, 7], [7, 8]]
}
```

- `gameId` 使用 `crypto.randomUUID()`；GitHub 评论 ID 是实际记录主键。
- `userId` 必须匹配 API 返回的 `author.id`，不能只信任正文。
- 黑方记录是房间根记录，白方申请通过 `hostCommentId` 引用它；白方不负责设置房间对手。
- 黑方通过 `opponentCommentId` 唯一确认白方；确认后不得在同一房间换人。
- 记录另含 `forbidden`（是否启用黑方禁手）和 `resigned`（本人是否认负/撤回），双方必须使用相同规则。认负保留本人的原有棋谱快照，避免违反快照末手归属。
- 新字段 `acknowledged/winner/reason` 表示本人已成功写入确认的终局结果。进行中为 false/null/null；终局 winner 为 black/white/null，reason 为 five/resign/draw。双方确认结果必须一致。旧 v1 缺失字段按未确认读取，后续编辑补齐。
- 状态包括 `waiting/playing/finished/cancelled`，属于辅助快照；配对和胜负以有效引用及棋谱推导。
- `moves` 保存本次写入时已知的完整棋谱；坐标采用 `[x,y]`、范围 `0..14`，数组下标决定黑白。
- API 返回的 `createdAt/updatedAt` 用于显示与清理，不采信正文自填时间。

棋谱合并约定：

1. 检查记录作者、房间引用、配对和 JSON 格式。
2. 重放棋谱，验证边界、重复位置、轮次以及终局后没有多余落子。
3. 黑方的非空快照必须以黑棋结束，白方的非空快照必须以白棋结束；空快照用于创建和申请。
4. 双方有效棋谱应为前缀关系；正常非空快照相差一手，配对初始允许都为空。
5. 使用较长的合法快照；不能因为另一条评论时间更新，就用短棋谱覆盖长棋谱。
6. 出现不兼容棋谱、异常长度差或历史回退时重新读取双方；仍异常则停止落子，显示数据异常。
7. 浏览器已有棋谱不得被较旧异步响应回滚。没有可信服务端时不承诺防止恶意伪造历史。

## 6. 大厅、配对与恢复

- 登录后分页扫描必要字段，按房主记录聚合房间及申请，推导有效对手和棋盘。
- 找到自己的未确认终局的有效对局或等待房间时自动进入；即使对方已确认结束，己方未确认时仍作为待同步棋局恢复。己方已确认时不在大厅显示，不阻止创建新局。未被接受的申请不算正在对局；多个有效房间在大厅选择。
- 大厅优先高亮本人等待/进行中的棋局，其他按有效房间双方的最大 `updatedAt` 降序显示；用背景区分等待、进行中和已结束。取消和异常记录不提供加入。
- 每张卡片只有一种点击行为，移除独立操作按钮。本人有未结束棋局时，进入本人棋局、旁观其他；没有时，加入等待房间、旁观其他。支持整卡点击与键盘操作。
- 创建按钮先弹出规则选择对话框，含黑方禁手、确定和取消。初始化/恢复会话/大厅刷新显示加载页，加载失败提供重试。对局显示明确阶段与落子提交 spinner，管理员区只在大厅。
- 创建前刷新并检查自己是否已有有效房间；创建请求使用固定 gameId，响应不明时先查询是否已创建，不盲目重发。
- 加入前重新读取房主；发表评论后进入“等待确认”，不立即允许落子。
- 房主在线前端自动选择按 GitHub `createdAt`、再按评论 ID 排序最早的有效申请，写入 `opponentCommentId`；申请者读取确认结果后开始。
- 未被接受者返回大厅并提示已被其他玩家加入；其申请保留，交由过期清理。
- 房主离线时不会自动接受申请。等待画面说明此限制；房主恢复页面后继续处理。
- 大厅仅展示等待/进行中的正常棋局及本人异常记录。进行中的玩家只提供认负，认负后停留最终棋盘，确认写入成功后才允许返回大厅；等待时取消/撤回直接删除己方记录，旁观者始终允许返回。
- 收到终局后立即提交本人确认；仅接收结果的玩家弹窗，产生结果的一方不弹窗，旁观者不弹窗。弹窗不阻塞数据同步；确认失败保留棋盘、禁止返回并允许重试，不重复提示。
- 客户端以 Web Locks（可用时）等轻量方式限制同账号同房间多标签页写入；不支持时给出提示，首版不承诺跨设备互斥。

## 7. 读取、轮询与提交

| 场景 | 策略 |
| --- | --- |
| 首次登录/手动刷新大厅 | 评论分页，每页最多 100 条，只取必要字段；完成后本地聚合 |
| 等待加入 | 默认每 5 秒检查新增顶层评论，缓存并去重申请 |
| 加入者等待确认 | 每 5 秒按 ID 读取房主及自己的评论 |
| 等待对手/旁观 | 单次 `nodes(ids: ...)` 查询读取双方评论，每 5 秒一次 |
| 轮到自己 | 暂停常规轮询，提供手动刷新；提交前和恢复焦点时刷新 |
| 隐藏标签页 | 暂停轮询，恢复可见后立即读取 |
| 终局未确认 | 自动提交确认，失败仍可手动/轮询重试；确认成功后停止轮询 |
| 结束/取消/退出对局/退出账号 | 停止对应轮询；回大厅时重新加载列表并检查己方补清理 |

等待加入的游标仅用于发现新评论，不能发现旧评论编辑。初始化建立游标和申请集合；游标失效或恢复会话时重新扫描。已选定对手后不再扫描整帖。首次读取和大厅刷新会扫描全量，所以不能以“最新创建的 n 条评论”代替“最近更新的 n 局”。

提交落子：锁定输入 → 读取双方最新状态 → 校验轮次与拟落子 → 编辑自己的评论 → 用 mutation 返回值更新界面 → 等待对方。

网络超时先重新读取自己的记录，核对目标棋谱是否已写入。编辑使用固定目标快照；重试前确认没有更新进展。未知结果的创建、加入请求用固定 gameId、作者和房主引用查重；重复有效申请按确定性规则归并。

每次轮询在上次请求结束后再安排下一次，防止重叠。页面切换、退出和身份变化时取消请求，丢弃旧会话响应。

## 8. 点数与错误处理

- 读取请求附带 `rateLimit { cost remaining resetAt }` 或检查额度响应头，显示余额和重置时间。
- 一次查询成本为 1 时，连续 5 秒轮询的名义预算约 720 点/小时；一次查询可同时读取两条评论。提交前刷新、分页、写入和其他应用另计。
- 不增加每次轮询前的独立额度探测；主额度与次级额度分别处理。
- 主额度不足时停止自动请求，等待重置或手动恢复；次级限流按 `Retry-After` 及 GitHub 指引退避，无提示时至少等一分钟，再指数退避。
- 解析 HTTP 错误及 HTTP 200 中的 GraphQL `errors`；部分返回数据不作为可落子的完整状态。
- 401/无效凭据提示重新登录；权限不足显示缺少的操作权限；评论不存在显示对局记录缺失。
- 本地网络异常保留最后棋盘，标注离线和上次同步时间，不允许离线提交。

## 9. 管理员清理

大厅加载还会自动补清理**己方**数据，删除前重新读取确认条件：A 双方 acknowledged 且 winner/reason 相同；B 己方已确认且对方记录明确不存在；C 未被接受的申请已失效（房主不存在、已取消或选择了别人）。旧版已取消的空房间也可清理。对方未确认时保留己方记录供其同步，普通缺失/权限错误、损坏或结果冲突不能当作已结束。删除失败留待下次加载，不影响大厅展示；不会自动删除他人数据。

- 管理员入口按配置的 GitHub node ID 显示；实际删除权限由 GitHub API 决定。
- 点击先全量读取并列出候选整局：双方已确认相同结果、安全的终局残留或失效申请可立即清理；其他仍按整组最大最后活动时间超过 30 天筛选。
- 同时列出过期未接受申请、已有根记录缺失的过期孤立申请；只处理 `gomoku-v1` 记录。
- 明确展示待删除记录、数量和最后活动时间，管理员确认后执行。
- 删除每局前重新读取根记录、对手记录及相关申请，重新校验整局过期条件和 `viewerCanDelete`；不将前端检查当作原子事务保证。
- 逐条顺序删除，写请求间隔至少 1 秒；报告成功、失败和跳过项目，允许重试。
- 清理在管理员页面打开期间运行，不实现关闭页面后的后台任务。

## 10. 实施顺序与验收

1. **认证与读写验证**：完成第 3 节真实账号联调，输出可复现配置说明与实际额度记录。
2. **协议与规则**：先实现纯函数和测试，覆盖前缀合并、轮次、终局和非法记录。
3. **大厅与配对**：完成登录门槛、分页列表、缩略图、恢复、创建、申请、确认和取消。
4. **棋盘与同步**：完成落子、双方按 ID 同步、旁观、提交确认和异常恢复。
5. **清理与站点接入**：完成管理员预览/删除、双语文案、移动端、目录入口及 README。
6. **整体联调**：两名玩家加一个旁观账号，真实演练开局、获胜、刷新恢复和清理；以测试数据替代真实旧对局验证 30 天筛选逻辑。

核心自动验证：横竖斜五连、长连和满盘；错轮、越界、重复棋子和终局后落子；短快照滞后不回滚、分叉拒绝；多人申请唯一配对；分页超过 100 条；创建超时不重复、编辑超时查证；旧异步响应丢弃；限流停止/退避；按整局活动时间筛选清理。

人工验收：两名非协作者能完成真实对局；第三人登录后旁观；刷新恢复到未结束对局；隐藏标签页停止轮询；token 失效重新授权；语言切换不丢局面；管理员只能删除授权的协议记录；现有本地五子棋和普通文章评论不受影响。

所有本地开发、测试和可审阅代码可先完成；外部控制台配置未完成时明确显示未配置状态，不把 mock 验证报告成真实账号联调通过。上线前填写公开配置并完成真实浏览器验收。
